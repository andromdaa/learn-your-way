# ADR-0015 — Add `quiz_id` to track items belonging to a section quiz

**Status:** Accepted
**Date:** 2026-04-30
**Deciders:** Cole (project owner), Claude Sonnet 4.6 (agent)

## Context

`POST /v1/attempts` returns `AttemptFeedback` that currently cannot surface
Glows/Grows commentary because there is no way to identify which quiz a
given attempt belongs to. Glows/Grows generation (T0c-r4) requires all
items from the same section quiz to be retrievable as a group.

Three possible linking strategies were considered:

1. **Nullable `quiz_id` on `assessment_items`**: stamp each item with the
   parent quiz's identifier at generation time. One extra nullable column;
   lookups are a single `WHERE quiz_id = ?` scan.
2. **Join table `quiz_items(quiz_id, item_id)`**: fully normalised; requires
   a separate insert per item plus a join on every lookup.
3. **Derive quiz membership from `attempts`**: identify items tried together
   in the same session. Fragile (a learner might skip items or retry them
   later) and requires heuristics.

## Decision

Add `quiz_id: str | None = None` as a nullable denormalised field on
`AssessmentItem` in `lesson_graph/models.py` and a matching `quiz_id TEXT`
column in the `assessment_items` and `attempts` SQLite tables.

- **`AssessmentItem.quiz_id`** defaults to `None`. Embedded MCQs (generated
  outside a section quiz context) retain `quiz_id = None`; they are not part
  of any quiz and do not participate in Glows/Grows feedback.
- **`SectionQuizGenerator.generate`** accepts an optional `quiz_id` keyword
  argument and threads it to each `MCQGenerator.generate` call.
- **`MCQGenerator.generate`** accepts an optional `quiz_id` keyword argument
  and stamps the value on every `AssessmentItem` it produces and persists.
- **`Database.get_items_by_quiz_id(quiz_id)`** retrieves all items with that
  `quiz_id`, used by T0c-r4 to feed the Glows/Grows generator.
- **`attempts.quiz_id`** mirrors the item's `quiz_id` at attempt-record time,
  enabling future analytics queries without a join.

The `quiz_id` value is a `uuid.uuid4()` generated by the caller of
`SectionQuizGenerator.generate` at quiz-generation time. Every item in the
quiz shares the same `quiz_id`.

## Why denormalised over a join table

A join table (`quiz_items`) is the fully normalised approach. It was
rejected because:

- The `quiz_id` relationship is write-once and never changes. There is no
  update path that would cause denormalisation anomalies.
- Denormalisation eliminates a join on the hot path: `WHERE quiz_id = ?` on
  a nullable indexed column is simpler than `SELECT item_id FROM quiz_items
  WHERE quiz_id = ?` followed by an `IN (...)` scan.
- The phase-3 scope does not require quiz-level metadata (title, created_at)
  beyond the identifier itself. If richer quiz objects are needed in a later
  phase, the `quiz_id` column is a natural foreign key to add at that time.

## Why `attempts.quiz_id` too

Mirroring `quiz_id` on the `attempts` table avoids a join when T0c-r4 needs
to correlate an incoming attempt with its parent quiz. The item's `quiz_id`
is already in memory at attempt-record time, so the cost is one nullable
column write per INSERT.

## Alternatives considered

### Join table `quiz_items(quiz_id, item_id)`

Fully normalised. Rejected for this phase — see "Why denormalised" above.
Revisit if quiz-level metadata (title, tags, creation timestamp) is needed.

### Derive quiz membership from session heuristics

Fragile and not implementable without a session concept, which does not
exist in the current data model. Rejected.

### Add `quiz_id` only to `attempts`, not to `assessment_items`

The item-level `quiz_id` enables `get_items_by_quiz_id`, which retrieves
the full item list for Glows/Grows generation without consulting the
`attempts` table. Omitting it from `assessment_items` would require a
join on every Glows/Grows generation call.

## Consequences

**Positive:**
- T0c-r4 can call `get_items_by_quiz_id` to retrieve all items for a quiz
  and feed them to `generate_glows_grows` without any schema changes.
- Embedded MCQs (quiz_id = None) are unaffected; the change is
  fully backwards-compatible.
- The new keyword-only argument on `SectionQuizGenerator.generate` and
  `MCQGenerator.generate` does not break existing callers.

**Negative:**
- Denormalisation: if a `quiz_id` needs to be renamed or revoked, all
  matching rows in `assessment_items` and `attempts` must be updated.
  Acceptable because quiz membership is immutable after generation.
- `attempts.quiz_id` is redundant with `assessment_items.quiz_id` via
  the `item_id` FK. This is accepted redundancy for query simplicity.
