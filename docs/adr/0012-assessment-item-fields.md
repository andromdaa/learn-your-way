# ADR-0012: AssessmentItem.correct_answer and bloom_level Fields

## Status

Accepted

## Context

Phase 2 introduces two needs that require new fields on `AssessmentItem`:

1. **Correctness evaluation at attempt time.** `POST /attempts` must
   determine whether a learner's submitted answer is correct. The
   correct answer must be stored somewhere accessible to the endpoint.
   Options were: (a) a field on the model, (b) a separate
   `correct_answers` lookup table, or (c) re-running the generator at
   attempt time.

2. **Active learning validation.** The pedagogy rubric requires at
   least one application/analysis item per section quiz. The active
   learning validator must classify each item. Options were:
   (a) a `bloom_level` field set by the generator prompt,
   (b) using `difficulty == "hard"` as a proxy, or (c) a post-hoc
   LLM classification call at validation time.

## Decision

### correct_answer: str | None = None

Add `correct_answer: str | None` directly to `AssessmentItem`, defaulting
to `None`.

The field is MCQ-specific: for a multiple-choice item the generator
stores the correct option text verbatim so the endpoint can compare
`response == correct_answer` without a secondary query. For other item
kinds (`short_answer`, `matching`, `drag_drop_timeline`) the field is
left `None`; the endpoint handles `None` with a graceful fallback
rather than a 5xx.

A separate `correct_answers` table was rejected: it adds a join on the
hot path of every attempt, and the data is logically part of the item.
Re-running the generator was rejected: it is expensive, non-deterministic,
and would require storing the original prompt context.

### bloom_level: Literal[...] | None = None

Add `bloom_level` using the six-level Bloom's Taxonomy vocabulary
(`"remember"`, `"understand"`, `"apply"`, `"analyze"`, `"evaluate"`,
`"create"`), defaulting to `None`.

The MCQ generator prompt instructs the model to emit a `bloom_level`
value alongside the question. A `None` value (model omitted the field,
or item generated by a non-MCQ path) is treated as `"remember"` by the
active learning validator — the most conservative assumption, ensuring
untagged quizzes do not silently pass the section-quality gate.

`difficulty == "hard"` was rejected as a proxy: a hard recall question
is not an application item. Post-hoc LLM classification was rejected:
it adds latency, requires a second model call per item, and is harder
to test deterministically.

## Consequences

- Both fields default to `None` for backward-compatibility with
  serialised `AssessmentItem` instances that predate this ADR.
- The `POST /attempts` endpoint must branch on `correct_answer is None`
  and return a meaningful response (e.g. `correct: False, rationale:
  "Manual evaluation required"`) rather than raising.
- The active learning validator (`lyw_core/validators/section_quality.py`)
  must treat `bloom_level = None` as `"remember"`.
- The MCQ generator prompt (T8) is responsible for populating both
  fields. Items where the model omits either field are discarded by
  the generator before persistence.

## Related clarification

`ConceptNode.prerequisites` is ordered by priority: index 0 is the
highest-priority prerequisite. This was implicit in the phase-1
implementation and is now made explicit in the field's `description`
argument and in `docs/02-data-model.md`. It does not constitute a
schema change in the sense of a new field or type, so no separate ADR
is warranted.

## Alternatives considered

**Separate `correct_answers` table**: normalised but adds a join on the
attempt hot path with no structural benefit for a single-user system.

**`difficulty` proxy for Bloom's level**: low implementation cost but
semantically wrong — hard recall is not application. Would produce
false positives in the active learning validator.

**Post-hoc LLM classification of bloom_level**: avoids a schema change
but adds latency, non-determinism, and test complexity. The generator
is the right place to classify because it already has the full item
context.
